# 05 - 日志系统设计与实现

在构建生产级别的Web应用时，一个设计良好的日志系统至关重要。本文将探讨miniblog项目中日志系统的设计与实现。

## 1. 日志系统的核心需求

一个优秀的日志系统应该满足以下核心需求：

- **结构化日志**：方便机器处理和分析
- **不同日志级别**：区分不同严重程度的日志信息
- **上下文信息**：记录请求ID、用户ID等上下文信息
- **性能影响小**：日志记录对主业务逻辑的性能影响应尽可能小
- **灵活配置**：能够根据不同环境调整日志级别和输出
- **追踪错误**：对于错误日志，能够记录详细的堆栈信息

## 2. 日志系统的设计

### 2.1 日志级别

miniblog实现了常见的几种日志级别：

- **Debug**：调试信息，仅在开发环境使用
- **Info**：一般信息，记录正常的操作过程
- **Warn**：警告信息，表示可能出现的问题
- **Error**：错误信息，表示操作失败
- **Fatal**：致命错误，记录后程序终止运行

### 2.2 结构化日志格式

传统的日志通常是简单的字符串，不便于机器处理。结构化日志则采用如下形式：

```
[时间] [级别] [调用者] 消息 键1=值1 键2=值2 ...
```

例如：

```
[2023-06-14 15:04:05.123] [INFO] miniblog/handler.go:42 用户登录成功 username=admin ip=192.168.1.1
```

这种格式便于日志采集工具解析，也便于人工阅读。

### 2.3 上下文关联

通过中间件为每个请求生成唯一的请求ID，并将其传递到整个请求处理链中，使得我们可以追踪单个请求的完整日志。

```go
// 获取请求ID的示例
requestID := c.GetString(known.XRequestIDKey)
```

## 3. 日志系统的实现

### 3.1 日志结构定义

```go
// Options 包含配置日志的选项
type Options struct {
	Level             string   // 日志级别
	Format            string   // 日志格式 (json 或 console)
	OutputPaths       []string // 日志输出路径
	DisableCaller     bool     // 是否禁用调用者信息
	DisableStacktrace bool     // 是否禁用堆栈跟踪
}

// Logger 定义日志记录器
type Logger struct {
	level             string
	format            string
	outputs           []string
	disableCaller     bool
	disableStacktrace bool
}
```

### 3.2 初始化日志系统

```go
// Init 初始化日志系统
func Init(opts *Options) {
	mu.Lock()
	defer mu.Unlock()

	// ... 初始化代码

	logger = &Logger{
		level:             level,
		format:            format,
		outputs:           outputs,
		disableCaller:     disableCaller,
		disableStacktrace: disableStacktrace,
	}
}
```

### 3.3 记录不同级别的日志

```go
// 记录info级别日志
log.Infow("Starting server", "addr", ":8080")

// 记录带有请求上下文的日志
log.C(c).Errorw("Database connection failed", "err", err)
```

### 3.4 日志中间件

日志中间件是一个关键组件，它会：

1. 记录每个请求的信息（方法、路径、耗时等）
2. 根据响应状态码决定日志级别（200->INFO, 400->WARN, 500->ERROR）
3. 捕获请求和响应体，在错误时记录详细信息

```go
// Logger 中间件使用示例
g.Use(middleware.Logger())
```

## 4. 日志最佳实践

- **为日志消息选择明确的描述**：比如用"用户登录失败"而不是"操作失败"
- **在错误日志中包含详细上下文**：包括错误信息、堆栈跟踪、输入参数等
- **避免在循环中记录日志**：这会产生大量重复日志
- **使用日志级别控制日志量**：生产环境通常设置为info或warn级别
- **结构化键名保持一致**：如始终使用"err"而不是混用"error"、"err"等

## 5. 日志与错误处理的结合

在miniblog中，日志系统与错误处理系统密切结合：

```go
// 创建带堆栈的错误
err := errno.Wrap(errno.ErrDatabase, errno.ErrDatabase.Code, "连接数据库失败")

// 记录详细错误日志
log.Errorw("处理请求失败", "err", err, "user", username)

// 返回友好的错误响应
errno.WriteResponse(c, err, nil)
```

## 6. 日志配置管理

通过配置文件和环境变量，可以灵活调整日志行为：

```yaml
# config.yaml
log:
  level: debug                 # 日志级别
  format: console              # 日志格式
  disable-caller: false        # 是否显示调用者
  disable-stacktrace: false    # 是否禁用堆栈
  output-paths:                # 日志输出路径
    - stdout
    - ./logs/app.log
```

## 小结

一个良好设计的日志系统不仅能帮助开发人员调试应用，还能在生产环境中快速发现和定位问题。miniblog项目实现的日志系统通过结构化日志、上下文关联和灵活配置，为应用提供了全面的日志解决方案。
